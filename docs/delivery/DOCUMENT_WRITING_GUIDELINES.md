# AgentHub 交付文档编写指南

本指南用于沉淀 AgentHub 交付文档的编写原则，供后续续写 `docs/delivery/PRODUCT_DESIGN.md`、`docs/delivery/TECHNICAL_DESIGN.md` 以及同类答辩交付材料时复用。

交付文档的目标不是重复研发文档，而是面向评审者清晰说明：AgentHub 解决了什么问题、采用了怎样的产品与技术设计、相比同类方案有哪些创新，以及这些结论如何从当前仓库的文档、代码和提交记录中得到验证。

## 1. 适用范围

本指南适用于以下文档：

| 文档类型 | 典型文件 | 主要读者 | 写作重点 |
| --- | --- | --- | --- |
| 产品设计文档 | `docs/delivery/PRODUCT_DESIGN.md` | 产品评审、课程评审、Demo 观看者 | 产品定位、使用场景、交互逻辑、创新体验、用户价值 |
| 技术设计文档 | `docs/delivery/TECHNICAL_DESIGN.md` | 技术评审、开发者、答辩问答 | 架构边界、运行机制、数据模型、事件协议、安全模型、工程特色 |
| 交付补充材料 | `docs/delivery/*.md` | 后续协作者、答辩准备者 | 结构化说明、写作规则、演示线索、复用清单 |

本指南不替代 `docs/README.md`、`AGENTS.md` 或架构文档。若本指南与仓库通用文档规则冲突，以仓库通用文档规则为准。

## 2. 基本原则

1. **事实先行**：每一小节动笔前，必须先确认相关事实来源。不能凭记忆、聊天印象或外部总结直接写结论。
2. **文档分工清晰**：产品设计文档讲设计哲学、用户体验和产品逻辑；技术设计文档讲工程机制、模块边界和实现依据。
3. **正式交付语气**：使用正式、完整、专业的中文表述，避免口语化堆叠，也避免过度营销化。
4. **丰富但克制**：能用表格、Mermaid、短代码块说明清楚的地方优先结构化表达，但不能为了“丰富”而堆图或堆代码。
5. **逐节推进**：只编写用户当前指定的章节或小节。除非用户明确要求，不主动大面积续写后续章节。
6. **保持既定结构**：用户已经确认过的标题、顺序和粒度应当保留；需要调整结构时，先说明原因和影响。
7. **创新点要有承载**：创新点不能只写口号，必须说明它解决的用户问题、设计逻辑，以及在仓库中可验证的功能或架构依据。
8. **外部建议只作线索**：OpenCode、Codex 或其他模型给出的总结只能作为候选线索，最终表述必须回到仓库文档、代码、`package.json` 或 git 记录验证。

## 3. 事实依据要求

### 3.1 优先事实来源

写作时按下列优先级确认事实：

| 优先级 | 来源 | 用法 |
| --- | --- | --- |
| 1 | 当前 `docs/` 文档 | 确认产品范围、架构边界、API 契约、事件协议、ADR 决策 |
| 2 | 仓库代码实现 | 验证功能是否真实存在，确认模块、目录、数据流、运行时机制 |
| 3 | `package.json` | 验证技术选型、运行脚本、依赖体系，不凭印象写技术栈 |
| 4 | git 提交记录 | 总结演进路线、提交次数、长期特性建设过程 |
| 5 | 仓库统计脚本 | 写代码行数、文件数、工程规模等量化指标 |
| 6 | 外部模型总结 | 仅作为待验证线索，不作为最终事实 |

### 3.2 必查材料示例

| 写作主题 | 建议查阅文档 | 建议查阅实现 |
| --- | --- | --- |
| 总体架构 | `docs/architecture/ARCHITECTURE.md`、`docs/adr/ADR-001-sidecar-architecture.md` | `hub-server/`、`agent-runtime/`、`web/` |
| 产品结构 | `docs/architecture/WEB.md`、产品设计文档已有章节 | `web/src/` |
| Agent Runtime | `docs/architecture/AGENT_RUNTIME.md`、`docs/architecture/AGENT_ARCHITECTURE.md` | `agent-runtime/src/agents/` |
| Orchestrator | `docs/architecture/AGENT_TOOLS.md` | `agent-runtime/src/agents/`、`agent-runtime/src/tools/` |
| 外部 Agent | `docs/external_agents/*.md` | `agent-runtime/src/external-adapters/` |
| RunEvent 与投影 | `docs/contracts/RUNTIME_SSE_EVENTS.md`、`docs/architecture/RUN_EVENT_SCHEMA_AND_PROJECTION.md` | HubServer 持久化与前端 Timeline 相关实现 |
| Skill / MCP | `docs/architecture/SKILL_MCP_SERVICES.md` | Runtime capability / MCP 相关实现 |
| 生产分发 | `docs/architecture/PRODUCTION_DISTRIBUTION.md`、`docs/architecture/BUN_RUNTIME_PACKAGING.md` | `cli/`、`desktop/`、构建脚本 |

### 3.3 冲突处理

如果发现文档和代码不一致，不能直接选择其中一方写入交付文档。应先记录冲突：

| 冲突类型 | 处理方式 |
| --- | --- |
| 文档写了但代码未实现 | 标注为设计目标或后续演进，不写成已完成能力 |
| 代码实现了但文档未更新 | 说明需要补充对应研发文档，再决定是否纳入交付文档 |
| 命名不一致 | 优先采用当前仓库中最稳定、最正式的命名，并在必要时说明别名 |
| 外部总结与仓库不一致 | 以仓库事实为准，外部总结不进入正文 |

## 4. 产品设计文档写作规则

产品设计文档的核心任务是说明 AgentHub 的产品判断，而不是解释代码如何运行。

### 4.1 应当强调的内容

- 用户为什么需要 AgentHub。
- AgentHub 如何用 IM 范式降低多 Agent 协作门槛。
- 会话、Agent、产物、权限、部署如何被组织成连续体验。
- 产品结构、页面布局和关键交互为什么这样设计。
- 创新点如何转化为用户可感知的效率、安全性和协作体验。

### 4.2 应当避免的内容

- 不展开具体类名、函数名、文件名和依赖包名。
- 不用长代码块解释产品功能。
- 不把技术实现细节写成产品价值本身。
- 不把未实现能力写成已经具备的产品特性。

### 4.3 图表规则

产品文档可以使用 Mermaid 和 Markdown 表格。对于页面结构、布局草图、交互空间关系等 Mermaid 表达不直观的内容，可以使用 fenced code block 的字符画，便于后续手动画图。

示例：

```text
+----------------+----------------------+----------------------+
| 会话列表       | 聊天 Timeline        | 产物工作台           |
| 搜索 / 置顶    | 消息 / 审批 / 任务   | Diff / 部署 / 预览   |
+----------------+----------------------+----------------------+
```

产品文档中的图表应当服务于设计表达，而不是展示代码调用链。

## 5. 技术设计文档写作规则

技术设计文档的核心任务是说明 AgentHub 如何被工程化实现，以及这些实现为什么支撑产品目标。

### 5.1 应当强调的内容

- Web、HubServer、Agent Runtime、CLI/Desktop 的职责边界。
- Sidecar Runtime、事件流、数据持久化、权限审批、工作区运行时等核心机制。
- Provider/Model、外部 Agent Adapter、Skill/MCP、Deploy Runtime 等扩展体系。
- 高风险能力如何被隔离、审批、记录和恢复。
- 生产分发、测试验证、工程规模和技术优势。

### 5.2 可使用的表达元素

| 元素 | 使用场景 | 约束 |
| --- | --- | --- |
| Mermaid | 架构图、时序图、状态机、依赖关系、运行时流程 | 技术文档优先使用 Mermaid |
| Markdown 表格 | 职责对比、选型理由、协议字段、风险控制 | 表头要明确，避免过宽 |
| 短代码块 | API 形态、事件片段、配置片段、关键接口 | 只放关键片段，不通篇长代码 |
| 列表 | 设计目标、机制拆解、验证步骤 | 避免过深嵌套 |

### 5.3 代码块规则

技术文档可以使用代码块，但应满足以下要求：

- 只展示能说明关键设计的最小片段。
- 不粘贴完整文件、完整类或大段实现。
- 优先展示接口形态、事件结构、配置样例或关键数据流。
- 代码块前后必须解释其设计意义。

## 6. 技术选型写作规则

写技术选型时，必须使用“技术选型”这一表述，不写成“技术选项”。

### 6.1 事实来源

技术选型必须从仓库中的 `package.json` 文件确认，包括但不限于：

- 根目录 `package.json`
- `web/package.json`
- `hub-server/package.json`
- `agent-runtime/package.json`
- `cli/package.json`
- `desktop/package.json`

不要凭印象写依赖，也不要因为某技术常见就默认项目使用了它。

### 6.2 结构要求

技术选型小节至少从三个角度展开：

| 角度 | 写作重点 |
| --- | --- |
| 前端 | Web/Desktop 体验、UI 体系、状态管理、构建方式、桌面适配 |
| 后端 | HubServer API、持久化、进程管理、事件推送、生产托管 |
| AI 运行时 | Agent 执行、模型调用、工具系统、外部 Adapter、MCP/Skill、部署运行时 |

同时应明确 AgentHub 是 **Bun 全栈项目**：开发、运行、服务端、Runtime、CLI 和生产打包均围绕 Bun 组织。

### 6.3 版本号规则

除非用户明确要求，不在交付文档中写依赖版本号。交付文档应关注技术选择和理由，而不是锁定包版本。

推荐写法：

| 技术方向 | 选型 | 理由 |
| --- | --- | --- |
| Runtime | Bun | 统一开发、运行、打包和分发链路，降低多进程本地应用的环境复杂度 |

不推荐写法：

```text
项目使用 xxx@1.2.3、yyy@4.5.6、zzz@7.8.9。
```

## 7. 仓库统计与 Git 信息写作规则

当需要在文档开头加入仓库规模、代码行数、提交次数等信息时，必须现场运行命令，不复用旧数字。

### 7.1 建议指标

| 指标 | 建议来源 |
| --- | --- |
| 提交次数 | `git rev-list --count HEAD` |
| 贡献者数量 | `git shortlog -sn HEAD` |
| Git 跟踪文件数 | `git ls-files` |
| 代码行数 | 仓库统计脚本 |
| TypeScript 文件数与行数 | 仓库统计脚本 |
| Markdown 文档数与行数 | 仓库统计脚本 |
| 核心目录规模 | `web/`、`hub-server/`、`agent-runtime/`、`docs/` |

### 7.2 代码行数脚本

优先使用仓库当前实际存在的统计脚本。当前仓库可使用：

```powershell
bun .\scripts\count_lines.js
```

如果脚本文件名发生变化，以 `scripts/` 目录下实际文件为准。写入文档的数字应说明统计口径，避免评审者误解。

## 8. 图表使用规则

### 8.1 技术文档图表

技术文档优先使用 Mermaid，适合以下场景：

| 图类型 | 适用内容 |
| --- | --- |
| `flowchart` | 架构边界、模块关系、数据流 |
| `sequenceDiagram` | 请求链路、审批续跑、事件推送、部署过程 |
| `stateDiagram-v2` | Run 生命周期、权限状态、部署状态 |
| `classDiagram` | 数据模型、接口关系 |

Mermaid 节点包含括号、斜杠、冒号等标点时，应使用引号包裹节点文字，避免渲染失败。

### 8.2 产品文档图表

产品文档可以使用：

- Mermaid：表达协作链路、用户流程、状态流转。
- Markdown 表格：表达页面结构、创新点对比、用户价值。
- 字符画代码块：表达页面布局、工作台空间关系和后续手动画图草稿。

### 8.3 图表质量要求

- 每张图必须有明确目的，不能只是装饰。
- 图前应说明它要表达什么，图后应补充关键结论。
- 图中的命名应和正文标题保持一致。
- 如果 Mermaid 无法清晰表达页面布局，宁可使用字符画。

## 9. 小节编写流程

后续每次编写具体小节时，建议遵循以下流程：

1. **确认本轮范围**：只写用户指定章节，例如“第 3 节”或“4.5 Timeline 设计”。
2. **读取事实来源**：先读相关 `docs/`，再查必要代码、`package.json` 或 git 记录。
3. **提炼本节结论**：把事实归纳成 2 到 5 个核心判断，避免罗列实现细节。
4. **选择表达形式**：判断是否需要表格、Mermaid、短代码块或字符画。
5. **落入文档**：保持已有标题层级、编号和语气一致。
6. **自查口径**：确认没有把未实现内容写成已实现，没有把技术细节误写进产品文档。
7. **运行轻量校验**：检查 Markdown 标题、格式和 diff。

建议在动笔前形成一个很短的事实依据清单，例如：

```text
本节依据：
- docs/architecture/AGENT_RUNTIME.md
- docs/external_agents/EXTERNAL_AGENT_ADAPTERS.md
- agent-runtime/src/external-adapters/
- git log --oneline -- agent-runtime/src/external-adapters
```

该清单不一定进入最终正文，但应作为写作前的内部依据。

## 10. 创新点写作规则

创新点应采用“标题正式、摘要清晰、证据明确、价值落地”的写法。

### 10.1 标题规则

标题应适合正式交付文档，避免过于口语化。可使用以下表达方式：

| 普通说法 | 更适合交付文档的说法 |
| --- | --- |
| 丝滑 UI 动效 | 高质感交互反馈与细腻动效体验 |
| 接入外部 Agent | 统一外部 Agent Adapter 体系 |
| 部署功能 | 面向发布交付的 Deploy 智能体与 SSH 运行时 |
| 事件保存 | 双层事件模型与可回放协作链路 |

### 10.2 内容结构

每个创新点建议包含：

1. 一句话定义核心创新。
2. 它解决的产品或技术问题。
3. 它在 AgentHub 中的设计逻辑。
4. 可选图表或表格。
5. 与同类方案相比的差异或优势。

### 10.3 证据规则

创新点必须能被至少一种仓库事实支撑：

- 产品文档或原始需求可以支撑“为什么需要”。
- 架构文档可以支撑“为什么这样设计”。
- 代码实现可以支撑“是否已经落地”。
- git 记录可以支撑“该能力如何演进成熟”。

## 11. 外部分析材料使用规则

OpenCode 或其他模型扫描仓库后给出的标题、结构和分析，可以帮助发现写作角度，但必须经过二次处理：

| 外部材料内容 | 使用方式 |
| --- | --- |
| 标题建议 | 可改写为更正式的交付文档标题 |
| 功能点罗列 | 逐条回到仓库验证，确认是否已实现 |
| 架构判断 | 对照 `docs/architecture/`、ADR 和代码边界 |
| 技术优势总结 | 融入相关小节的“技术特色”或“设计价值” |
| 未验证细节 | 不进入正文，或明确写为后续方向 |

外部分析材料不能替代事实核查。

## 12. 验证与收尾

文档修改完成后，至少进行以下轻量校验：

```powershell
git diff --check -- docs/delivery/<file>
Select-String -LiteralPath docs/delivery/<file> -Pattern '^(##|###|####) '
```

如新增文档，也应检查 git 状态：

```powershell
git status --short
```

文档类修改通常不需要运行测试。最终回复中应说明：

- 新增或修改了哪个文档。
- 文档沉淀了哪些可复用规则。
- 是否运行了格式或结构校验。
- 未运行代码测试的原因，例如“仅文档变更，未运行测试”。

## 13. 快速检查清单

后续每次续写交付文档前，可以使用以下清单：

| 检查项 | 是否必须 |
| --- | --- |
| 本节是否已经确认事实来源 | 必须 |
| 产品文档是否避免过多技术细节 | 必须 |
| 技术文档是否解释了工程机制和设计理由 | 必须 |
| 技术选型是否来自 `package.json` | 涉及时必须 |
| 是否避免写依赖版本号 | 必须，除非用户要求 |
| 是否尽量使用表格、Mermaid 或短代码块增强表达 | 建议 |
| Mermaid 是否适合当前表达目标 | 必须判断 |
| 字符画是否仅用于 Mermaid 难以表达的产品布局 | 涉及时必须 |
| 是否只写用户要求的章节 | 必须 |
| 是否保留用户已确认的结构 | 必须 |
| 是否运行 `git diff --check` | 修改后必须 |
