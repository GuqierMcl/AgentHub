# 智能体头像自定义设计

## 1. 背景

当前 AgentHub 的智能体头像由前端共享 resolver 在本地推导：

- 系统预设智能体通过固定 `agentId` 命中图标或静态资源。
- 外部智能体可命中少量前端静态资源预设。
- 未命中预设的智能体使用 `shortName/name/id` 计算 initials，并基于 hash 选择颜色。

现状有两个限制：

- 头像不是平台事实，前后端契约中没有头像字段。
- 用户无法为任意智能体设置更符合个人偏好的头像样式。

本设计目标是在不修改智能体定义本体、不引入账号级同步的前提下，为所有智能体提供本机个人偏好的头像覆盖能力。

## 2. 设计目标

本期目标：

- 支持 `system`、`external`、`user` 三类智能体自定义头像。
- 头像覆盖是独立于智能体只读/可编辑状态之外的平台级本机偏好。
- 支持三类头像来源：上传图片、图标选择、首字母样式。
- 头像文件与映射文件都保存到用户目录，路径规则与 `setting.json` 一致。
- 所有消费头像的前端入口统一复用一套覆盖解析逻辑。

本期非目标：

- 不实现跨设备同步。
- 不实现多用户共享同一头像覆盖配置。
- 不将头像覆盖写入 Agent Runtime 的 agent definition。
- 不实现头像历史版本管理。
- 不复用 conversation artifact 体系承载头像图片。

## 3. 用户体验

### 3.1 编辑入口

- 在智能体详情页头部头像区域附近提供独立的 `自定义头像` 按钮。
- 该入口对所有智能体可见，包括系统预设智能体和外部智能体。
- 该入口不受智能体本体是否可编辑影响，因为它表示“我的显示偏好”，而不是“编辑智能体定义”。

### 3.2 编辑方式

点击 `自定义头像` 后，打开统一弹窗，使用三标签结构：

- `上传图片`
- `选择图标`
- `首字母样式`

弹窗交互约束：

- 顶部始终显示实时预览。
- 切换 tab 只更换编辑控件，不重置当前预览。
- 底部固定提供 `恢复默认`、`取消`、`保存`。

### 3.3 展示范围

头像覆盖生效后，以下区域应立即一致更新：

- 智能体列表卡片
- 智能体详情页
- 新建会话弹窗中的智能体选择项
- 聊天会话头部
- 聊天消息中的智能体头像
- 其他复用共享 `AgentAvatar` 组件的区域

## 4. 作用域与职责边界

### 4.1 作用域

头像自定义的作用域为“当前本地应用实例的个人偏好”：

- 仅对当前机器上的 AgentHub 生效。
- 其他用户不会看到该覆盖结果。
- 不依赖登录态或 HubServer 多用户共享存储。

### 4.2 职责边界

- `web`：负责展示、编辑、预览和提交头像覆盖。
- `hub-server`：负责头像覆盖配置读写、文件落盘、图片安全处理与图片读取接口。
- `agent-runtime`：不参与头像覆盖逻辑。

该边界符合现有 `web -> hub-server -> agent-runtime` 分层：头像属于产品层个性化配置，不属于 AI 执行面能力。

## 5. 存储设计

### 5.1 存储根目录

头像覆盖目录放在 `config.dataDir` 下，路径规则与 `setting.json` 一致。

示例：

```text
<config.dataDir>/
  setting.json
  avatar-overrides/
    manifest.json
    files/
      coder/
        current.webp
      reviewer/
        current.svg
```

说明：

- `config.dataDir` 沿用 HubServer 现有用户目录解析规则。
- `manifest.json` 保存 `agentId -> avatar override` 映射。
- `files/` 保存上传后实际生效的头像文件。

### 5.2 manifest 结构

建议结构：

```json
{
  "version": 1,
  "updatedAt": "2026-06-03T12:00:00.000Z",
  "agents": {
    "coder": {
      "source": "icon",
      "icon": "code2",
      "tone": "blue"
    },
    "reviewer": {
      "source": "initials",
      "text": "RV",
      "tone": "emerald",
      "shape": "rounded"
    },
    "opencode": {
      "source": "image",
      "file": {
        "relativePath": "files/opencode/current.svg",
        "mimeType": "image/svg+xml",
        "width": 256,
        "height": 256,
        "size": 18231
      }
    }
  }
}
```

设计约束：

- `version`：manifest 版本号，便于后续平滑迁移。
- `updatedAt`：整个 manifest 最后更新时间。
- `agents`：以 `agentId` 为 key。
- 未配置的 `agentId` 不写入，直接回退默认头像逻辑。

## 6. 头像类型设计

### 6.1 image

用于上传图片后生效的头像。

字段：

- `source: "image"`
- `file.relativePath`
- `file.mimeType`
- `file.width`
- `file.height`
- `file.size`

### 6.2 icon

用于从平台支持的图标库中选择图标。

字段：

- `source: "icon"`
- `icon`
- `tone`

其中：

- `icon` 为受控枚举，必须来自前端和后端约定的可选图标集合。
- `tone` 表示头像色板。

### 6.3 initials

用于用户定义文字和样式。

字段：

- `source: "initials"`
- `text`
- `tone`
- `shape`

其中：

- `text` 建议限制为 1 到 2 个可显示字符。
- `shape` 第一版可支持 `circle`、`rounded` 两类。

## 7. 渲染优先级与回退规则

所有头像显示统一遵循以下优先级：

```text
HubServer 头像覆盖 -> 当前前端默认预设 resolver -> initials/hash fallback
```

具体规则：

- 若 `agentId` 存在覆盖配置，则优先使用覆盖配置。
- 若覆盖不存在，则继续走现有前端默认预设逻辑。
- 若默认预设未命中，则继续走 initials/hash fallback。

异常回退规则：

- manifest 文件不存在：视为无覆盖。
- manifest 文件损坏：HubServer 返回空覆盖并记录日志。
- 图片文件不存在或不可读：前端自动回退默认头像。
- 图标 id 不合法：前端自动回退默认头像。
- initials 配置字段缺失：前端自动回退默认头像。

目标是“头像覆盖失败不影响主界面渲染”。

## 8. HubServer API 设计

### 8.1 `GET /api/avatar-overrides`

用途：

- 返回完整 manifest 的前端消费视图。
- 前端初始化时拉取一次并缓存在内存中。

返回建议：

```json
{
  "version": 1,
  "updatedAt": "2026-06-03T12:00:00.000Z",
  "agents": {
    "coder": {
      "source": "icon",
      "icon": "code2",
      "tone": "blue"
    }
  }
}
```

### 8.2 `PUT /api/avatar-overrides/:agentId`

用途：

- 写入 `icon` 或 `initials` 类型覆盖。

请求体建议支持两种结构：

```json
{
  "source": "icon",
  "icon": "code2",
  "tone": "blue"
}
```

```json
{
  "source": "initials",
  "text": "RV",
  "tone": "emerald",
  "shape": "rounded"
}
```

### 8.3 `POST /api/avatar-overrides/:agentId/image`

用途：

- 上传图片并写入 `image` 类型覆盖。

请求格式：

- `multipart/form-data`

行为：

- 验证 `agentId` 是否存在于当前可见智能体集合中。
- 校验文件类型、大小与内容。
- 将文件保存到用户目录。
- 更新 manifest。

### 8.4 `DELETE /api/avatar-overrides/:agentId`

用途：

- 删除该智能体的覆盖配置并恢复默认头像。

行为：

- 删除 manifest 中该 `agentId` 对应项。
- 最佳努力删除其头像文件目录。
- 即使文件删除失败，也应优先保证 manifest 已删除。

### 8.5 `GET /api/avatar-overrides/:agentId/file`

用途：

- 返回当前生效图片型头像的二进制内容。

约束：

- 仅用于 `image` 类型。
- `icon` 和 `initials` 类型不需要该接口。
- 若该 agent 当前不是 `image` 类型，返回稳定错误。

## 9. 图片处理规则

### 9.1 支持类型

第一版支持：

- `png`
- `jpg`
- `jpeg`
- `webp`
- `gif`
- `svg`

### 9.2 位图处理

对 `png/jpg/jpeg/webp/gif`：

- 限制单文件大小，建议上限 `5MB`。
- 在 HubServer 侧统一标准化处理。
- 标准化输出格式建议为 `webp`。
- 标准化尺寸建议为 `256x256`。
- 最终只保留当前版本文件，例如 `current.webp`。

### 9.3 SVG 处理

对 `svg`：

- 保留 SVG 形态，不强制转位图。
- HubServer 在保存前必须做安全清洗。
- 清洗目标包括：
  - 去掉脚本执行能力
  - 去掉危险外链引用
  - 去掉潜在事件处理属性
- 最终保存为 `current.svg`。

理由：

- SVG 的核心价值是矢量清晰度和可缩放性。
- 直接转为位图会损失其优势。
- 但 SVG 自带脚本和外链风险，因此必须由服务端清洗。

## 10. 前端集成设计

### 10.1 状态获取

前端新增头像覆盖查询：

- 在 agents 模块和 workbench 模块初始化时请求 `GET /api/avatar-overrides`。
- 将结果缓存在 TanStack Query 中。

### 10.2 组件改造

共享 `AgentAvatar` 组件新增“覆盖配置”输入能力，推荐两种实现方式之一：

- 由上层显式传入 override
- 由共享 hook/context 从 query cache 读取 override

推荐使用共享 hook/context，减少各处重复传参。

### 10.3 保存后的刷新

保存成功后：

- 直接更新本地 query cache
- 立即让所有依赖 `AgentAvatar` 的界面生效
- 不要求整页刷新

## 11. 校验与错误处理

后端校验：

- `agentId` 必须存在于当前可见智能体列表中。
- `icon` 必须属于允许集合。
- `text` 必须满足显示长度限制。
- 图片上传必须满足类型和大小限制。

错误处理原则：

- 返回结构化稳定错误码。
- 不允许因头像覆盖错误影响智能体主功能。
- manifest 写入使用原子写，避免中途中断导致文件损坏。

## 12. 安全性

关键安全要求：

- 头像能力只属于 HubServer 产品层，不下放到 Agent Runtime。
- 图片文件只允许保存到用户目录约定子目录。
- 不允许客户端传入任意绝对路径。
- SVG 必须经过服务端清洗。
- 图片读取接口只暴露 HubServer 控制下的头像资源，不暴露任意文件读取能力。

## 13. 测试建议

后端建议验证：

- 读取空 manifest。
- 写入 `icon` 覆盖。
- 写入 `initials` 覆盖。
- 上传位图并生成标准化文件。
- 上传 SVG 并完成清洗保存。
- 删除覆盖后 manifest 回退。
- manifest 损坏时回退为空配置。

前端建议验证：

- 所有头像消费入口都能正确读取覆盖结果。
- 保存后无需刷新即可生效。
- 删除覆盖后正确恢复默认头像。
- 图片文件缺失时能平稳回退。
- 系统智能体和外部智能体都能进入头像设置弹窗。

## 14. 推荐实现路径

推荐按以下顺序实施：

1. HubServer 头像覆盖存储与 manifest 读写
2. HubServer 基础 CRUD API
3. 前端头像覆盖查询与共享解析逻辑
4. 智能体详情页 `自定义头像` 弹窗
5. 图片上传、SVG 清洗与即时预览
6. 全链路校验与回退测试

## 15. 结论

本方案将“头像自定义”定义为一层独立于智能体定义本体的本机个人偏好覆盖，并把持久化职责放在 HubServer 用户目录下，与 `setting.json` 采用同一数据根目录规则。

该方案的核心优点是：

- 支持所有智能体自定义头像
- 不破坏现有只读/可编辑模型
- 不污染 agent definition
- 不引入账号同步复杂度
- 可以以最小侵入方式复用现有 `AgentAvatar` 共享渲染链路
